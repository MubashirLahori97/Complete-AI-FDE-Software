# Mission 1: Make a useful website

Stage 1: Build with AI and understand the result

A useful site you can open and explain, with AI allowed to create every file.

AI can perform all implementation, research, planning, tests and diagnosis. Concepts are compulsory. This is a mission, not a one-day guarantee.

## The problem

A neighbourhood repair service answers the same questions every day: what do you fix, where do you work, and how do I contact you? Start with a small, accurate information site. Use a fictional business until you have permission to use real details.

## Understand the concepts

### Outcome and implementation

An outcome is what someone can accomplish. Implementation is the machinery that makes it possible. Tell AI the visitor's task and the limits before choosing a tool. A beautiful page that omits the service area has missed the outcome.

**Example:** A visitor can find the service area and contact method without asking you.

**Common wrong idea:** A screenshot proves the website works. It only shows one view; links and small screens still need checking.

### Browser and technology stack

A browser reads page structure, applies styles, and runs browser behaviour. Hosting makes files available to other devices. A stack is the collection of technologies actually used. A simple site can use HTML and CSS with no database or live AI. AI helping you build is different from AI running inside the product.

**Example:** HTML supplies a contact link; CSS gives it a clear appearance; the browser follows it.

**Common wrong idea:** Every website needs a backend. An information site may only need hosted files.

## Predict, change, observe

A visitor presses Contact. Choose what the button actually does.

Prepared teaching simulation, not live provider or business evidence. Predict before selecting.

- **No destination:** The page stays here. The visitor cannot contact the service. A visible button needs a real behaviour. Appearance alone is insufficient.
- **Open an email draft:** The visitor's configured mail app can open a draft. Nothing has been sent. An email link hands off to another app; it is not a server sending a message.
- **Show a phone number:** The visitor can read the number and choose whether to call. This is a simple useful outcome without a database or account.

Flow: Visitor opens URL (Visitor's device) → Site files arrive (Hosting → browser) → Browser displays page (Visitor's device)

## Worked example

**before:** The heading says Welcome and the contact button has no destination.

**action:** Ask AI to name the repair service, show its area and hours, and use a clearly labelled contact link.

**after:** A visitor can answer the three common questions and reach a contact option.

**lesson:** Inspect the actual files with AI. If the product only contains static files, explain those files rather than inventing a server.

Authored example; your project requires its own observations.

## Project: Your first useful service site

Create a small information website for a repair service or another useful local service. It must show services, area, hours and a working contact option. Use truthful fictional details and no payment or private data.

1. Choose who your page is for and the one thing they need to do. Ask an AI builder or coding assistant to create the page and explain how to open it.
2. Open the result yourself. Ask AI to improve one confusing part and show which files and technologies make the page work.
3. Try the page on a narrow screen and using a keyboard. Save the files or a preview you can reopen. Choose hosting later when you are ready to publish.

## Understanding, separately from output

- **explain:** Explain the difference between the visitor's outcome and the files AI generated.
- **locate:** Find the actual page, its styles and its hosting or local preview. What is absent?
- **predict:** If hosting is unavailable, can a new visitor load the site? What about an already loaded page?
- **compare:** Compare a static site with an app that stores enquiries. Why choose one now?
- **challenge:** AI says the contact button stores messages in a database. What would you inspect or try to establish whether this is true?

## Reviewer guidance

Ask the learner to open their own contact action, trace it, and identify actual technologies. A copied diagram with an imaginary database needs revision.

AI stays available. A working output plus generated prose does not establish understanding if the learner cannot apply the concept. Practise these variations, then ask a reviewer for a fresh relevant variation:

- The owner changes the service area. Show which result must change and verify it.
- A visitor has no mail app configured. Explain the limitation and propose another contact option.

Record who or what reviewed, the learner's predictions and reasoning, observed results, gaps and next practice. Local review records are not authenticated qualifications.
