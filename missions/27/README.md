## Understand the concepts

### Architecture as responsibilities and tradeoffs

Architecture describes responsibilities, boundaries and dependencies. Coupling is how strongly one part depends on another. Modularity can make change easier, but extra services also add operations and failure boundaries. Choose complexity proportionate to the outcome.

**Example:** One application may fit a small workflow better than several separately deployed services.

**Common wrong idea:** More layers always mean more professional architecture.

### Evidence-linked delivery

Delivery combines implementation, checks, configuration, access and a usable result. AI may perform the whole technical sequence. Keep the system explanation synchronized with meaningful changes and distinguish actual observations from planned checks.

**Example:** A claimed enquiry feature needs evidence that the enquiry reaches the chosen destination.

**Common wrong idea:** A generated system description is accurate because the app looks complete.

## Predict, change, observe

Change the prepared architecture for a small information-only service.

Prepared teaching simulation, not live provider or business evidence. Predict before selecting.

- **Static site fits the need:** Explain files, browser behaviour and hosting. No invented backend is needed. The explanation must match the actual product's responsibilities.
- **Needs shared private records:** Add suitable storage, identity and trusted permission boundaries. The requirement adds responsibilities beyond a static page.
- **Add many services anyway:** More configuration and failure boundaries without an established benefit. Complexity needs a reason connected to constraints.

## Understanding, separately from output

- **explain:** Explain the architecture and how its boundaries serve the outcome.
- **locate:** Identify every important technology in actual files, configuration or service settings.
- **predict:** Choose one failed component and predict what the user and stored state would show.
- **compare:** Defend an important technology choice against a simpler or more portable alternative.
- **challenge:** AI's diagram includes an unused service. Explain how to verify and correct the description.
