# Lesson 27 project — An evidence-based portfolio case study

## The customer problem

Choose one completed learning project and package it for a reader who has no context. Write a concise case study, verify the repository and demo links, include a representative test report, and explain your own contribution. Use the app's portfolio tracker to keep the artifacts together and export a readable copy.

**Learning goal:** Explain a project's problem and your contribution to a new reader. Support outcome claims with traceable evidence or clearly labelled estimates. Package a reproducible demo, repository, and case study.

**Scope:** build the core version first. The starter is a worked example, not a finished solution to the full project. Use fictional or public sample data.

## What to deliver

- A problem-first case study with scope and contribution.
- Verified project links or a clearly documented local demo.
- A representative test/evaluation record and actual result.
- A small implementation diagram and explicit limits.

Include a short README with the purpose, setup steps, example use, known limitations, and the evidence from your test cases. A reviewer should be able to tell which parts you implemented and which parts are demonstrations or mocks.

## Build it in milestones

### Milestone 1: Choose the story

- Select a project with inspectable behavior and evidence.
- Write the user problem and resulting change in plain language.

**Stop and check:** The topic is more specific than a list of tools.

### Milestone 2: Gather proof

- Connect claims to tests, source versions, and observed outputs.
- Label fixtures, assumptions, and your contribution honestly.

**Stop and check:** Every numerical claim has traceable support or an estimate label.

### Milestone 3: Review as a stranger

- Verify setup and links in a clean context.
- Ask a new reader which claim remains unclear and revise it.

**Stop and check:** The case study stands alone without your chat history.

## Acceptance checks

- [ ] The case study states a specific user problem and resulting behavior.
- [ ] Your implementation and decision contribution are clear.
- [ ] Outcome claims link to evidence or are labelled estimates.
- [ ] Demo/repository setup or local-delivery instructions are verified.
- [ ] The architecture, limitations, and next step match the actual project.

These are the same checks shown in the app. Record the actual result and relevant evidence, rather than checking a box because the code looks plausible.

## Test matrix

| Case | Action or input | Expected behavior |
| --- | --- | --- |
| 1 | Reader has no prior context | Problem and result remain understandable |
| 2 | Inspect a numerical claim | Dataset, denominator, or estimate assumptions are provided |
| 3 | Open demo and repository links | They lead to the described version or a clearly stated local setup |
| 4 | Compare diagram with implementation | No planned-only component is presented as completed |

Run the normal path and the failure paths. Keep a failed result visible in your notes until you understand and fix it. Re-run earlier passing cases after a change to catch regressions.

## Starter and how to use it

The download contains this brief, a small worked example named `case-study.md`, and its expected output. Replace the prompts with evidence from one of your actual learning projects. This starter is a writing artifact.

Read the example before extending it. Keep your own project in a separate working directory or repository. Do not store secrets, real customer information, or private documents in a public learning repository.

## Stretch challenges

- Record a short walkthrough showing a normal and a failure case.
- Write an alternative explanation for a non-technical customer audience.

Choose an extension only after the acceptance checks pass. Describe what the extension changes in the data model, user flow, tests, or operating cost.

## Review rubric and reflection

- Which claim is best supported by your evidence?
- What should the reader not assume about this project?
- What concrete feedback improved your explanation?

Score yourself on four areas: correctness against the brief, clarity of the implementation, useful failure handling, and strength of the evidence. For each area, record one thing that works and one thing you would improve. A polished screenshot alone does not establish that the project works.

Finish with a short case study: **Problem → Approach → Tests → Results → Limitations → Next step.** Distinguish measured results from estimates. Record your evidence in the app's Record your build tab and keep a link to the project.
